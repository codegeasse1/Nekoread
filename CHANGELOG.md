# Changelog

All notable changes to Nekoread.

## [2.2.7] - 2026-09-09

### Tag/genre taps now land on the results (take twenty)
- **Tapping a genre tag on a manga detail screen left you looking at the detail screen - the tag search had run, but into the Browse entry *behind* it.** The tap called `viewModel.openTagSearch(...)` and then `navController.navigateToTab("browse")`, and `navigateToTab` navigates with `popUpTo(startDestination) { saveState = true }` + `restoreState = true`. The restored state is a tab's whole saved back stack - and the saved Browse stack still held the manga detail screen that was open on top of it - so Browse came back with the tag search applied *underneath* that restored detail entry. The grid was rendering (the log shows `[browse] composed=gridCardx9` while the detail was on screen); you just could not see it until you pressed back and popped the detail entry, which is exactly the "navigate back to see the results" you described.
  - Fixed with a dedicated `navigateToTagSearch()` instead of `navigateToTab`: it pops straight back to the existing Browse entry (`popBackStack("browse", inclusive = false)`), dropping everything stacked above it, so the tag results become the visible screen immediately; if Browse is not on the stack at all (the detail was opened from Library or History), it pushes a fresh Browse with `launchSingleTop` and no state restore.
  - A tag search now also selects the catalog's **Filter** mode, so the Filter chip matches the filtered grid (the tag branch of `searchCatalog` ignores the mode, but the chip was previously left on "Latest" while showing tag-filtered results).
  - The log now traces the whole tap in case anything is still off: the tap logs `tag click tag=… src=… from=<route>`, the navigation logs `tag click -> popped back to browse` or `tag click -> pushed browse (not on the stack)`, and the Browse screen logs `tag search apply src=… tag=…` with the tab it switched to.

### Reader long-strip pages rendering black (take nineteen)
- **The stretching fix is confirmed, but some long strips came out solid black - this build stops routing them through the chunked renderer.** The dx21 log and screenshots pin it: the pages that render fine log `path=TALL_WHOLE` and decode in 0-2ms (`decoded … bitmap=720x13715 … tallWhole=true`), while every page that comes out black logs `path=TALL_CHUNKED`. The Comix source serves 720px-wide strips running 13.7k-17.0k px tall, i.e. whole-strip bitmaps of **37.7-46.7 MiB**, which straddle the reader's arbitrary 40 MiB single-decode budget: the two shortest strips (003 = 720x13715, 008 = 720x14425) fit and render, and every taller one (001, 002, 004, 005, 006, 007, 010) fell to the windowed-chunk renderer. The budget is now **48 MiB**, so the whole realistic range decodes through the proven single-bitmap path at the source's own 720px resolution; it is still a per-bitmap cap, and the total is bounded by Coil's memory cache (~102MB on this device, which was already holding two 39.5MB strips). When a strip is over the budget even at 48 MiB, the reader now **halves the decode width** (Coil only subsamples by powers of two, so requesting half the last width is what actually halves the bitmap) and takes the whole-strip path at the largest reduced width that fits - only a strip that will not fit even at 256px wide is handed to the chunked renderer. In practice that path is now unreachable for normal webtoon pages.
- **The chunked renderer no longer throws its work away on every re-bind.** `WebtoonChunkedImageView.setChunkedImage` unconditionally ran `cancelAll()` (cancel the layout build and the decode loop, drop every decoded chunk) - and RecyclerView re-binds/re-attaches a holder every time it leaves and re-enters the screen, plus the reader re-binds every visible holder on a render-setting change. The dx21 log shows page 1's chunk layout being built **five times in a few seconds**; with a 15k-px strip's chunk decodes taking longer than the gap between re-binds, the page never accumulated more than a chunk or two, which is exactly a black field (no spinner, no error - the page's top few rows had decoded, the rest had not). `setChunkedImage` is now idempotent for the same file + decode parameters: it keeps the built layout and its decoded chunks and just re-targets the window, and only tears down when the file or the decode parameters actually change. `onDetachedFromWindow` likewise stops the jobs but **keeps the built chunk layout**, so a page that scrolls out and back resumes decoding into it instead of re-running the bounds decode and re-laying out the strip (the decoded bitmaps are still released while detached, so off-screen holders cannot pin memory).
- **A failed chunk is now visible in the log, and gets one retry.** `decodeChunk` discarded the exception (`runCatching { … }.getOrNull()`), so a region decode that failed was indistinguishable from one that had not run yet - and a failed chunk was never retried, leaving a permanent hole. Decode failures now log `chunked decode FAILED idx=… rows=…: <Exception>: <message>`, a chunk that fails outside the viewport is retried once when it re-enters the decode window, and the draw path emits a rate-limited `chunked GAP n/m drawn chunks missing (range …) decoded=…/… failed=…` line, so any remaining black band names the exact chunk indices responsible. A new `chunked ready (first chunk i of n)` line confirms the chunked path actually produced pixels.
- **Reader diagnostic lines are now attributed to the right page.** `WebtoonChunkedImageView` emitted its `chunked info:` line through `ReaderDiagnostics.log`, which tags with the shared `currentLabel` - whatever page bound most recently. That is why the dx21 log appeared to show page 6's chunk layout never being built: the line was there, relabelled under a neighbouring page. The chunked view now carries the bind-time label and uses `logFor`, so `chunked …` lines read at face value.

### Reader page stretching + thumbnail brightness (take eighteen)
- **Long-strip pages are no longer vertically stretched in the reader.** `WebtoonChunkedImageView` rendered a pathologically tall strip as `partCount` chunk bitmaps drawn into *equal* display slots (`slotH = viewHeight / partCount`), i.e. every chunk was scaled to the same height regardless of how many source rows it actually held. The chunks do not hold equal rows - `chunkHeight` (2048) almost never divides the strip's decoded height - so the last chunk (which holds the remainder, sometimes a few hundred rows out of several thousand) was inflated to a full half of the screen. The draw is now mapped from the source pixels: the display scale is `viewWidth / sourceWidth`, and chunk `i` is drawn at `[srcTop(i), srcBottom(i))` in source rows, so every chunk appears at the page's true aspect ratio, contiguous, with no gaps and nothing stretched. `chunkStep()` now returns that same per-chunk display height, so the decode window and the nearest-chunk targeting are exact instead of a `viewHeight / partCount` approximation.
- **A page's frame height now uses the width the image is actually laid out at.** The holder sized each strip with `recycler.width * h / w`, but the frame is inset by the webtoon side padding on both sides - so with any side padding set, every page's slot was taller than the page's own aspect, which the chunked renderer used to fill by stretching vertically (and which left a gap under every short page). A new `pageWidthPx()` (recycler width minus both side paddings) is used for all three height calculations (the cached-size fast path, the bind-time target, and the post-download correction).
- **Grid covers are no longer black across the bottom half.** take seventeen's scrim was a `Transparent -> 85% black` ramp over the cover's lower 55%, which left the bottom third of every library/catalog thumbnail essentially black - measured on the tester's screenshot, ~33/255 luminance against ~118 at the top of the same cover, i.e. a visibly dull half-thumbnail on every cell. The hoisted brush now carries explicit stops (fully transparent to 58% of the cover, then a gentler ramp to 50% black at the bottom edge) and is drawn over the whole cover node, so the artwork stays visible while the rating star and the `Read` pill keep their contrast.

### Library & catalog scroll jitter (take seventeen)
- **The log can now tell measure from draw, per item type.** take sixteen cut the worst library/catalog frames from 500-900ms to mostly 50-250ms, but the remaining spikes still read as an anonymous `anim` phase. This build adds `Modifier.cellCost(tag)`, which times a node's measure pass (`tag.m`) and its draw pass (`tag.d`) with zero extra layers, and `AppDiagnostics` aggregates them per frame into a new `cells=` digest on both `msg` and `frame` lines, e.g. `cells=card.m 14x9ms(max 41) card.d 14x3ms(max 7)`. The library grid card (`card`), the list card (`listCard`), the library hero (`hero`) and the detail chapter row (`chrow`) carry it, so the next log says outright whether a frame is 14 cells spending 9ms each in measure, two cells cold-drawing, or neither (pure `input`-dominated lazy `forceRemeasure`), which are three different fixes.
- **Grid/list cards are now a single drawing node.** `border(...) + background(color, shape)` each built a modifier node and each re-created its paint/shader on every size change; both are folded into one `drawWithCache` (`cardSurface`) that draws the rounded fill plus an inset rounded stroke behind the content. The bottom scrim rides the cover `AsyncImage`'s own `drawWithContent` instead of being a sibling `Box`, and the read-progress bar — previously a track `Box` wrapping a clipped inner `Box` (three layout nodes plus a clip layer) — is now two `drawRoundRect` calls in the single reserved 7dp `Box` via `drawBehind`.
- **The Library hero is no longer Material3.** The `Continue Reading` banner was a `Card(elevation = 4.dp)` + a Material3 `Button` + an `Icon(PlayArrow)`: a Card is a `pointerInput` + `Modifier.surface` + an elevation shadow + a content-colour `CompositionLocalProvider`, and a Button adds a Surface, a Row, minimum-interactive-size, ripple and another provider — for a static rounded rectangle and one label. It is now a plain `Box` with `clip` + `background` + `border` and a hand-drawn primary pill (`Box` + `Text("▶ Resume")`), with the four text styles hoisted to file-level constants that reproduce `Type.kt` exactly. This is the hero the take-sixteen log showed costing ~140ms to compose (`msg 143ms composed=herox1` → `frame anim=145ms`).
- **The manga-detail screen stops rebuilding its images (and fades) on every pass.** The hero background, the hero cover card and *every chapter row* each built an inline `ImageRequest.Builder(ctx).data(coverModelFor(manga)).crossfade(true).build()` — so every recomposition of every row re-resolved the cover model, allocated a request and started a new fade animation, for the same thumbnail repeated down the whole list. The three requests are now hoisted and `remember`ed, the chapter list shares one non-crossfading `chapterThumbRequest`, and the hero cover card uses the grid's own key/size (`cover:<id>`, 360x500) so it reuses the bitmap the library already decoded instead of decoding its own.
- **The detail screen's Material3 containers are gone.** The hero cover card (`Card(elevation = 8.dp)`) is a clipped `AsyncImage`; the type/status chips were two `Surface`s and are now `Text` with a clipped background; the genre tags were `Surface(onClick = …)` and are now a clickable `Box`; and each chapter row's read/bookmark toggles were two `IconButton`s and are now 44dp clickable `Box`es around the same `Icon`s (same targets, same tints). The hero gradient `Brush` and the chapter row's text styles are hoisted out of composition. Also fixed the two visible `"… • …"` strings that were stored as mojibake and rendered as `â¢`.

### Library & catalog scroll jitter (take sixteen)
- **A grid cell now composes in a fraction of the nodes it used to.** The dx18 log finally names the cost: the lazy grid's prefetch scheduler composing **3 cells** held the main thread for 75ms (`msg 75ms …AndroidPrefetchScheduler`), the long `[scroll library]` frames are `anim`-phase (recomposition) with `layout`/`draw` near zero, and `composed=gridCardxN` rides exactly those frames. That is ~15-25ms of composition per cell on this device — one dropped frame per row entering the viewport. A card is now built from plain `Column`/`Box`/`Text` instead of Material3 `Card` + up to three nested `Surface`s: each `Surface`/`Card` wraps its cell in a `CompositionLocalProvider`, a `Modifier.surface` and (M3 1.3) a per-card `pointerInput`, i.e. nodes that existed purely to paint a chip, a badge and a pill. The card is the same shape, border and colours (`border` → `background` → `clip`, the same order `Modifier.surface` uses, with the text colours that used to be inherited from the `Card`'s content colour now set explicitly).
- **The two `Icon`s drawn on every cell are gone.** The rating's star and the Read pill's play triangle were `Icon(imageVector = …)`, each building a `VectorPainter` plus a Box/Canvas/semantics per cell. The rating is now a single `Text` whose gold star is a `SpanStyle` (and whose `AnnotatedString` is `remember`ed, so it is built once per rating, not per composition), and the pill is one `Text("▶ Read")` instead of a Row + Icon + Spacer + Text.
- **The per-cell `LinearProgressIndicator` is a two-`Box` bar.** `LinearProgressIndicator` brings a state holder, progress semantics, a `graphicsLayer` and a draw-with-cache node per cell — several nodes per item for a static 0.6 fraction.
- **Per-cell allocations are now file-level constants.** `MaterialTheme.typography.x.copy(...)` allocated a fresh `TextStyle` for every `Text` in every cell, and the cover scrim re-created a `Brush` (and its Shader) for every cell; both are hoisted (the hoisted styles reproduce `Type.kt` exactly — SansSerif + the same sizes/lineHeights/letterSpacings). The app root's background/glow `Brush`es are hoisted the same way.
- **The hero no longer shares its memory-cache key with the grid.** `memoryCacheKey("cover:<id>")` was used for the hero (1080x560), the grid (360x500) and the list (180x240) alike, so a cover first decoded for the hero was handed to a 130dp grid cell and pinned ~600k pixels per manga in the cache. The hero has its own `cover-hero:<id>` key now.
- **Diagnostics attribution fix (so the next log is readable).** `msg …ms` lines now carry the `composed=` digest of the compositions that happened *inside that message*; before, the digest was drained on the next reported frame, whose phases no longer contained the work — which is why the worst frames looked like `anim` with nothing composed and the prefetch message looked anonymous. This build's log should show a per-cell composition cost well under half of dx18's.

### Library & catalog scroll jitter (take fifteen)
- **The frame log now names the composable that recomposed.** dx17 cut the worst library/catalog frames roughly in half (worst 478->148ms) but the remaining long frames are still `anim`-phase with `layout=0` — i.e. Compose recomposition, not measure or decode — so this build attributes it: `AppDiagnostics.noteCompose(tag)` is called at the top of the library screen, the grid/list cards, the hero, the recents row, the catalog tab, the app root and the overlay, and every reported frame line now carries `composed=tagxN …` for the compositions that happened since the previous frame. The next log therefore says outright whether the spikes are grid-card compositions, a whole-screen recomposition, or nothing out of Compose at all.
- **The diagnostics overlay can no longer be the thing it is measuring.** The overlay rendered *all* `MAX_LINES` (400) lines — it re-joined and re-laid-out a ~40 KB paragraph every 400ms during precisely the scrolls it was watching. It now renders only the trailing 14 lines; the log file and the Copy button still carry everything.
- **Grid cells are now a constant height.** The title reserves two lines (`minLines = 2`) and the progress row keeps its 7dp even when a title has no reading progress, so every cell in the grid is exactly the same size. A variable cell height forces the lazy grid to measure each item to discover its extent; uniform cells let it compute extents without measuring.

### Library & catalog scroll jitter (take fourteen)
- **Thumbnail fade-in no longer runs during a fling.** The App-dx log for the library grid shows the long frames dominated by the `anim` phase (20-200ms) with `layout`/`draw` near zero — the signature of a Choreographer animation, not layout or decode work. Every cover was requested with `.crossfade(true)`, so each time a thumbnail landed a fade animation ran on the main thread; while flinging that is one per row entering the viewport. `MangaGridCard`/`MangaListCard` covers now load with **no crossfade** (the hero keeps its fade), removing the grid's continuous `anim` cost. The cover `ImageRequest` is also `remember`ed, so scroll recycling / recomposition reuses one object instead of re-allocating it each pass.
- **The list card's spinner is gone.** `MangaListCard` drew an indeterminate `CircularProgressIndicator` behind every row's cover; an indeterminate indicator animates forever on the main thread for as long as it stays composed — even once the cover has covered it — so it was a permanent animation source during a list fling. The tinted tile is the placeholder now, matching the grid.
- **The hero is no longer a `SubcomposeAsyncImage` with no size.** The Library "Continue Reading" banner decoded and uploaded its cover at full resolution into the widest cell on screen; it is now a plain `AsyncImage` over a tinted `Box` with a bounded `.size(1080, 560)` request, and its scrim `Brush` is hoisted to a file-level value instead of being rebuilt per recomposition.
- **Lighter per-cell drawing.** The grid card's full-cell bottom gradient is now a lower-55% scrim (the full-cell gradient was an extra fill every frame for no visual gain), the redundant `surfaceVariant` background under the aspect-ratio `Box` is removed (the `Card`'s container already paints it), and the rating text is `remember`ed instead of re-formatted on every recomposition.
- **Lazy items declare a `contentType`.** The library grid/list, the "Recently Read" row and the extension catalog grid now pass `contentType = "manga"`, so the lazy layouts can reuse a cell's composition across items rather than only across the same slot.
- **Fixed a stale `derivedStateOf` in the catalog's infinite scroll.** `shouldLoadMore` used a keyless `remember { derivedStateOf { ... } }`, so it captured the first composition's `hasMore`/`isLoadingMore`/`isLoading` and never saw them change — it could re-fire `onLoadMore` near the bottom edge (extra fetches and composition while the user was still flinging). It is now keyed on those flags.

### Reader open / initial-load (take thirteen)
- **The reader no longer binds the whole chapter at once when it opens.** The take-twelve log shows every page of the 18-page chapter binding in one burst on open (`bind seg=0 page=1` … `page=18`, ~100-150ms apart) — the tell-tale sign that the list was laid out with collapsed placeholders, so the entire chapter fit the layout window and RecyclerView created holders for all of it. The placeholder height came from `viewer.recycler.height`, which is **0** while the first holders are created (the adapter is built during the initial layout, before the recycler is measured), and a 0-height placeholder is coerced to **1px**. The holder now falls back to the display height until the recycler is measured, so a loading page occupies a full viewport and only the visible pages are bound.
- **Prewarmed pages are sized on the FIRST layout pass, not one frame later.** A page's frame height was only set inside the holder's load coroutine, after a `Dispatchers.IO` hop — so even a page whose bytes were already downloaded and whose size was already known first laid out at the viewport placeholder and then relaid out to its real height. Since the prewarm downloads pages well ahead, nearly every page is in this case, and that per-page relayout is the remaining initial-load jitter. The holder now reads the page's already-cached size **synchronously** during the bind (`WebtoonPageCache.cachedSize`) and sizes the frame in place, safe because the bind runs inside RecyclerView's own layout pass (`setFrameHeightNow` — mutates the existing params and only requests a layout when the recycler is *not* already laying out).
- **The prewarm warms page metadata too, not just the bytes.** After each download lands the loop now calls `WebtoonPageCache.prime`, which caches the page's dimensions and animated flag, so `cachedSize` has an answer for the very next bind (previously the animated-flag probe could force an IO hop on the bind path even when the dims were known).
- **Diagnostics line labels are now trustworthy.** Async lines (`file ready`, `decoded …`, `SSIV ready`) were tagged with the mutable global `currentLabel` — whatever page was bound *most recently* by the time the async callback ran — so a page's download/decode was attributed to a later page, which is what made the take-twelve log show the same page bound twice with two different sizes. `ReaderDiagnostics.logFor(label, …)` takes an explicit label captured at bind time, and every async callback (holder and `ReaderPageImageView`) uses it. The next log's per-page lines can be read at face value.
- Not ours: the ~9.6s of silence between the reader's first frame and the first page binding on open is the **chapter page-descriptor fetch through the Comix extension** (network/extension side, before any page exists) — nothing in the reader runs during it. Decodes are already off the main thread (`decoded 149-356ms config=HARDWARE`, two at a time) and memory is healthy (`memcache 56→94MB`, heap 36→46/256MB).

### App-wide performance (take twelve)
- **Every list is now free of per-cell `SubcomposeLayout`.** The new app-level diagnostics (take eleven) immediately found the app's two worst scroll surfaces — the **Library grid** and the **chapter lists** — stalling for 500-900ms per frame during a fling (`frame total=984ms` on the Library, `frame [scroll chapters] total=674ms`). Both, plus the reader's chapter picker, drew their image with `SubcomposeAsyncImage`: a `SubcomposeLayout` **per cell**, which is one of the most expensive layouts in Compose (each cell composes its content in a separate, deferred subcomposition, and re-measures on every state change). With one per grid card / one per chapter row that dominated the frame. They are now plain `AsyncImage` composables over a tinted parent `Box`, which shows through while loading and on failure (so the visual placeholder is unchanged): the grid keeps its flat `surfaceVariant` tile, the list card's spinner now sits *behind* the image, and the chapter thumbnails keep their tinted placeholder. Covers the Library grid/list, the "Recently Read" row, the extension catalog grid/list, the series chapter list, and the reader's chapter-picker sheet.
- **The Library's hero/recents are derived once per list, not once per recomposition.** `continueManga` (scan for the newest read) and `recentlyRead` (filter + full sort + take 8) were computed inline in the composable body, so any recomposition re-scanned and re-sorted the entire library on the main thread — remembered on `mangaList` now.

### Reader performance (comix lag — take eleven)
- **The reader no longer hits a ~500ms stall when the next chapter streams in.** Take ten's log confirmed the per-page stall is gone — pages 13-22 bind every ~100ms with no `recompose ReaderScreen` and no `msg …Choreographer…` lines between them — but it showed a new ~500ms hit at each chapter boundary (`recompose ReaderScreen 506ms` followed by `ui stall 595ms`, immediately before the next chapter's pages start binding). The cause: appending a chapter changes `streamSegments`, which rebuilds the webtoon adapter's item list, and `WebtoonAdapter.submit` ran `DiffUtil.calculateDiff` over the **entire** stream (every page of every already-streamed chapter) synchronously on the UI thread. A streaming reader only ever *appends*, so `submit` now detects that the old item list is a prefix of the new one and dispatches a single `notifyItemRangeInserted` (plus a trailer refresh) instead of diffing — O(pages added) instead of O(all pages). New `adapter append …ms` / `adapter diff …ms` log lines say which path ran, so the next log confirms it.
- **Preload widened back up, now that the real cause is known to be elsewhere.** Take four/seven deliberately shrank the read-ahead because the decoded-page churn looked like the jank; with the per-page main-thread stall fixed (take ten) that throttling was solving the wrong problem, so: the concurrent download batch went 6 → 8, the download window widened from 8 behind / 40 ahead to **12 behind / 60 ahead**, the memory-warm horizon from 4-8 ahead / 2 behind to **6-12 ahead / 3 behind**, and a page is re-warmed sooner (stale 3 → 2) so the deeper window survives LRU eviction. Warm *concurrency* deliberately stays at 1 — the two-wide decode pool is shared with the visible-page binds, and one warm in flight guarantees a bind always has a free slot — so the increase is depth, not parallelism.
- **New whole-app scroll diagnostics** (`App dx` overlay), the app-level counterpart to the reader tracker: it catches jitter and lag on **every** screen, not just the reader. An app-wide `FrameMetrics` listener reports the phase breakdown of any long frame, a single global `Looper` message probe names the exact callback that blocked the main thread (routed to the reader's buffer while in the reader, to the app's elsewhere), and a touch/scroll-gesture detector groups those frames into named scroll sessions with a per-gesture summary (`scroll <name> end <ms> frames=N janky=N worst=Nms`). Every line is tagged with the current nav route (`[browse]`, `[manga_detail/…]`, `[library]`, `[updates_history]`, …), and the library grid/list, history list, series chapter list and extension results grid are probed by name (`AppScrollProbe`). Same Copy/Clear overlay as the reader, shown on every screen except the reader (which keeps its own). Log: `nekoread-app-diagnostic.log`.

### Reader performance (comix lag — take ten)
- **The reader no longer recomposes on every page flip.** Take nine's log named the blocker exactly: a `recompose ReaderScreen` of 230-425ms, sitting inside a `Choreographer$FrameDisplayEventReceiver` frame callback (`msg …ms Handler (android.view.Choreographer$FrameHandler)`) and accounting for the whole `anim` phase of the ~250ms long frames — one per page bind. The cause was an upstream invalidation, not anything on screen reacting to the page: `MangaRepository.saveReadingProgress` writes the manga row *and* the chapter row on every page (`mangaDao.updateReadProgress` + `chapterDao.updateChapterReadState`), and the reader route collected both of those rows as live Room flows, so every page flip re-emitted a new `MangaEntity` and a new `List<ChapterEntity>`. Those are `ReaderScreen`'s parameters, so the whole screen (reader view + chrome + every argument and `remember`) re-executed once per page. Progress saving is now decoupled: the route reads a one-shot **snapshot** of the manga + chapter list when the reader opens or the chapter changes, and never subscribes to the rows the reader itself is writing. A page flip no longer invalidates any composition scope.
- Take nine's probes are kept for this build so the next log can confirm the fix directly: `recompose ReaderScreen` should not appear at all during a scroll, and the ~250ms `msg …Choreographer…FrameDisplayEventReceiver` lines should be gone. The `frame`/`delay`/`bind`/`prewarm` probes are unchanged.

### Reader performance (comix lag — take nine)
- **The frame probe now reports the pre-frame delay** (`delay=…`) alongside the phases. Take eight's log showed the ~250ms frames split into two shapes: some with `anim≈250ms` and everything else ~0 (the long work ran *inside* the frame's animation callback), and others with `anim≈5ms` but `total≈250ms` (the UI thread was already busy when the frame arrived). The new `delay` number makes that split explicit instead of inferred.
- **New main-thread message probe** (`msg <n>ms Handler (…) {callback}`): take eight proved the UI thread is blocked ~250ms at a time — roughly once per page bind — but the phase breakdown alone can't say *which* callback is doing it. The reader now installs a `Looper` message logger while it is on screen and reports any main-thread message that takes 60ms or more, naming the exact handler and callback class (a Choreographer frame callback, a RecyclerView runnable, a coroutine continuation, …). This is the probe that names the culprit rather than narrowing it.
- **New recomposition probe** (`recompose ReaderScreen <n>ms`) times this screen's own recomposition whenever it exceeds 40ms, so the next log settles whether the block is Compose recomposition or native view work.
- **New bind/prewarm probes** (`bind work <n>ms`, `bind sync <n>ms`, `onBindViewHolder <n>ms`, `prewarm tick <n>ms`) time every reader-owned main-thread path — the whole synchronous adapter bind, the page-holder's synchronous pre-launch section, its background-load coroutine body, and the preload loop's iteration body — so if the block is one of those it shows up by name even if the message probe can't attribute it.
- No behaviour changes in this build: it is a diagnostics build whose log should name the blocking call, so the fix can be made against the real cause instead of the two candidates (reader recomposition, page bind) narrowed down so far.

### Reader performance (comix lag — take eight)
- **Page changes no longer recompose the whole reader.** The last log showed the UI thread blocked for 260-430ms on nearly every page bind, while a lone decode of the same pages cost 14-70ms — so the time was going into the compose/layout pass, not image decoding. `currentPage` was being read at the top of the reader composable (as the progress-save effect's key, and as an argument to the chrome), which makes every page change invalidate the entire reader recompose scope — one large unskippable subtree that re-runs the webtoon `AndroidView` update, every argument expression and every `remember`. Progress saving now observes the page via a snapshot flow (read inside a coroutine, not during composition) and the chrome reads the page through provider lambdas evaluated in its own scope, so a page flip updates the pill and nothing else.
- **`WebtoonRecyclerView.scaleTo` no longer forces a layout pass on every call** — it now requests a layout only when the view's own height actually changed. Continuous mode calls this on config updates, and the unconditional layout request re-measured and re-laid-out the page frames even when nothing about the scale had changed.
- **Diagnostics now measure the frame phases.** New `frame total=… input= anim= layout= draw= sync= cmd= swap=` lines (only for frames over 100ms) name which phase is eating the frame — layout/draw in the app process, or sync/cmd/swap waiting on the GPU — so the next report tells us whether we are CPU-recomposing or render-thread/GPU bound instead of leaving us to infer it.
- The periodic `memcache` line now also prints live heap (`heap=<used>/<max>MB`) next to the cache size, so the next log shows whether the stalls coincide with GC pressure from a pinned memory cache.

### Reader performance (comix lag — take seven)
- **The reader's diagnostics no longer cost frames.** Every page event was logged by opening, writing and closing the log file **on the calling thread** — usually the main thread inside the page-bind callback — and by rebuilding a 120-line snapshot and recomposing the on-screen overlay **on every single line**. During a fling that is dozens of synchronous disk writes and string builds per second on the UI thread, which is scroll jank in its own right and also inflates the reported `decoded …ms` times (the bind's success callback is delayed by however long the UI thread was blocked, so a 50ms decode can *report* as 600ms). Lines now go to a background writer thread in batches, and overlay updates are coalesced to about two per second.
- **The loop's bookkeeping maps are no longer Compose snapshot state.** `webtoonDownloaded` / `webtoonInFlight` / `downloadFailed` were `mutableStateMapOf` (snapshot state) written on every download start/finish — pure main-thread snapshot overhead, since only the prewarm loop ever reads them. They are plain maps now.
- **Page-decode concurrency is capped at the two the device can take.** Take six gave the memory-warm-ups their own dispatcher so a bind could never queue behind one, but that let **three** decodes run at once — and the dx9 log shows exactly what that costs: three decodes landing together took 644-722ms each, versus ~50ms for a lone decode (and 120ms each when the same three ran without a fling competing). Warms share the binds' two-wide dispatcher again, with at most one warm at a time, so a bind always has a free slot and the pool is never oversubscribed.
- **Warm-ups pause during a scroll gesture.** While you are dragging/flinging, both decode slots belong to the pages actually entering the viewport; the moment the gesture settles the decode-ahead window refills. A page that enters the viewport mid-gesture cold-decodes in ~50ms, so nothing is starved.
- The log now also records main-thread stalls (`ui stall …ms`) measured from the reader loop's own tick gap, so the next report can tell UI-thread jank apart from slow page decodes instead of both showing up as a big `decoded` time.

### Reader performance (comix lag — take six)
- **Page binds no longer queue behind background warm-ups.** The warm and the on-screen bind shared one small decode dispatcher, so during a fling a page scrolling in had to wait behind whatever warm decodes were in flight and its own decode was reported as 300-680ms, even though a lone decode of the same page costs ~60ms. Warm-ups now run on their own one-at-a-time dispatcher, so a bind is never blocked by a warm (and total decode concurrency stays bounded: 2 binds + 1 warm).
- **The decode-ahead window now grows to cover a fling.** It was a fixed 4 pages, which the log showed a fast fling still outran (pages 16-19 entered together and cold-decoded ~380ms each). The depth is now derived from the memory-cache capacity — roughly half the cache, one decoded page each, clamped to 4-8 — so a big-heap device gets a long runway while a small-heap one can't overflow the cache and thrash. The warm tick is also faster (50ms idle / 90ms while scrolling) so the window refills the moment you pause.
- **Memory cache given a floor** so a small-heap device still holds the whole decode-ahead window instead of evicting the nearest pages (a 128MB heap at the old 40% held only ~13 pages).
- The diagnostics log now prints the memory-cache pressure (`memcache max=…MB size=…MB`) every couple of seconds, and each warm miss records its decoded size — so the next log pinpoints whether pages are still being evicted.

### Reader performance (comix lag — take five)
- **The decoded page is now sized to fit the page cache.** A 1080-wide page is ~2.0M pixels (~7.9MB as a hardware bitmap), so on this device the cache held only ~4-6 of them — fewer than the pages kept warm ahead of you plus the ones on screen. The warm window therefore evicted itself and every page you scrolled onto had to be decoded cold from disk: the log showed 300-680ms per page (and ~420ms each when three landed at once) instead of the ~1ms cache hit it should be. Short pages are now decoded at a bounded ~1.0M-pixel budget (~4MB, sampled slightly — comparable to the ~800px sources that always scrolled smoothly), so the whole warm window fits the cache and scroll-ins go back to being instant hits. Pages already at or below the budget are untouched, and the on-screen display size is unchanged.
- **Page decodes no longer stampede each other.** At most two page decodes run at once, so a fling pulling several pages in can't have a burst of 4MB decodes all slow to ~400ms from contention.
- **The warm-up runs again, paced to the gesture.** Gating it off during a scroll was the wrong call: the log showed it then almost never ran, so nothing stayed warm. It now keeps filling the window continuously — ticking fast while you read, slower while a drag/fling is in progress so the scroll keeps the CPU.
- **Binds no longer touch the disk on the main thread.** The page's dimensions come from the download metadata instead of up to three bounds-decode file reads per bind.

### Reader performance (comix lag — take four)
- **The memory warm-up no longer decodes while you scroll**: warming ran continuously, and even though each warm was a small 20-80ms background decode (binds were already 1ms cache hits), on a low-end device that background decode load during a drag/fling is what still hitch-scrolled. The warm now runs only in the pauses between scrolls (when you're reading a page) — the read-pause is long enough to fill the pages-ahead window, and the scroll gesture itself has the CPU to itself.
- **Far flings no longer outrun the pre-download window**: the window was 20 pages ahead, so a fast fling past it (the log showed a jump from page 14 to 40 waiting ~525ms at bind for the download) hit a blank page. The window is now 40 pages ahead, so the pipeline stays in front of a fling.

### Reader performance (comix lag — take three)
- **Long manhwa strips now decode ONCE, whole, at the display width** and are shown as a single stable bitmap — no more per-chunk region decoding / recycling while you scroll, which was the remaining jank even after the chunked-view rewrite. The render thread tiles the single software bitmap and caches its textures, so a fling through a long strip is now just one cached image being drawn each frame.
- **Fixed the black bars breaking long strips**: the old chunked view drew each chunk into fixed 2048px slots while the chunk's real displayed height was smaller (power-of-two sampling almost always overshot the view width), leaving a solid black gap between every chunk — the "images are breaking" bars. Tall strips no longer use the chunked view at all except for pathological mega-strips, whose chunk slots are now equal and seamless (each chunk tiles its exact display slot, so there are never gaps).
- **Chunked fallback (mega-strips >40MB) is stable now**: decoded chunks are kept for the page's lifetime (no re-decode/upload churn when you scroll back), memory is bounded by recycling only the chunks farthest from the viewport, per-chunk failures no longer blank the page unless they happen where you're looking, and region decoding (which Android can only do into software bitmaps — the old "hardware chunk" attempt silently fell back to software every time) is done explicitly as ARGB_8888/RGB_565.
